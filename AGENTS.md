# FixLang — Instructions

## Overview

Local macOS menu-bar app: fixes grammar and improves writing on selected text via AI (OpenAI, OpenRouter, AWS Bedrock, Ollama, LM Studio). Electron + React + TypeScript, runs on **bun**.

Current release: **v0.19.5**.

## Main Features

What the user gets. Implementation traps for each area live under [Known Gotchas](#known-gotchas) — read the matching skill before touching it.

- **Transform** — select text in any app, press a preset hotkey, get the rewrite back. Delivery is either **Direct paste** (replaces the selection) or **Show popup** (leaves the source alone): global in Settings → General → Transform output, overridable per preset.
- **Selection read** — every hotkey, Ask AI included, reads the selection the same way: snapshot the clipboard, **empty it**, send Cmd-C, poll the pasteboard for content, then use what the copy produced — **or the snapshot when it produced nothing**. Two separate things are going on and both are load-bearing. **The emptying** exists because polling for a *change* cannot tell "nothing was selected" from "the selection is byte-identical to what was already on the clipboard"; against an empty pasteboard both collapse into one question, so `selectionChanged` finally means "the app copied something". **The fallback** exists because the answer to that question, on real hardware, is often no: across two days of one machine's logs, **not one read produced text the clipboard did not already hold** — every transform that appeared to work was running on text the user had copied by hand. A version that removed the fallback (0.19.3) turned every one of that user's transforms into `No text selected`. So the fallback is not a nicety covering a rare case; for a user whose habit is copy-then-hotkey it is the entire feature, and the copy is the optimisation. **Ask AI gets the same fallback, and the source travels with the text** (`AskContextSource`, `getAskContext`) — the input window labels a clipboard-sourced context `From clipboard` instead of `Selected text`. That label is what makes attaching it acceptable at all: Ask has no "nothing selected" abort, so an unlabelled stale clipboard would be text the user never chose, silently sent. Labelled, in a window they must still type into and submit, it is an offer they can decline with Esc. An earlier version refused the fallback outright on exactly that leak reasoning — sound premise, wrong conclusion, because it protected a feature that then had no context on any press. `""` still means no context and no card. **The log key is `selectionChanged`, never `clipboardChanged`**: `redactLogContext` blanks any key merely *containing* `clipboard`, so the obvious name persisted as `"[REDACTED]"` and the one field that could have diagnosed all of this was blank in the logs that showed the bug. Same trap as the `selectionPoll` latency phase. `Ask context resolved` (`contextLength`/`contextAttached`/`contextSource`, lengths only) is the line that says which source won. **What the fallback cannot answer, the stale-clipboard guard does**: a fallback read is `selectionChanged: false`, and that flag is exactly what `evaluateSelectionGuards` keys on — so a snapshot older than the configured age limit is refused instead of transformed, and a genuine selection (`true`) is never age-checked at all. The fallback and the guard are one design, not two: keeping the fallback is what makes an ancient clipboard reachable, and the age limit is what stops it arriving unnoticed. See **Security guard rails** below.

- **Presets** — seven built-ins, each with its own hotkey: Correction (`Control+Shift+F`), Summarize (`Control+Shift+S`), Prompt optimization (`Control+Shift+D`), Translate (`Control+Shift+T`), Business Writing (`Control+Shift+B`), Context-Aware Structured Text (`Control+Shift+R`), Ask AI (`Control+Shift+A`). Custom presets too. Every preset carries its own model (from any connected provider), system prompt, reasoning effort (`none`/`low`/`medium`/`high`) and output mode (`inherit`/`paste`/`popup`).
- **Ask AI** — the one preset that needs no selection: its hotkey opens a small input window, treats any current selection as optional context, and answers in a cascading popup (up to 5 at once) that reads selection → question → answer. Selection and question are plain text clamped to 3 lines; only the answer is GFM markdown, and it is never clamped. Nothing selected means no selection block at all. The Show more/less control sits *after* the text and renders only when the clamp actually truncates it — measured from the laid-out element (`scrollHeight > clientHeight`), never guessed from string length, since line count depends on popup width. That measurement runs **only while collapsed**: expanding drops the clamp, so re-measuring there would report "fits" and unmount the control the user needs to collapse again. jsdom lays nothing out and has no `ResizeObserver`, so the test stubs both. The **input** window folds the attached selection the same way, one line instead of three (520x200, and the textarea is the point of it), expanded capped at `max-h-16` with its own scroll because the window never grows; the footer keeps the `Context attached · N chars` count, which the ellipsis cannot convey. Its fold control is a real focusable `<Button>` placed **before** the textarea, so a forward Tab from the input can never land on it and Tab stays the ghost's. The card is labelled (`Selected text`, `data-ask-context-label`, uppercase over the text it labels) the way the session-detail chat labels its system prompt: unlabelled, a block of someone else's text above the question box does not explain itself — and the same card is the only place the user can check WHAT is attached before sending it.
- **Source-app context** — the frontmost app name ("Slack", "Mail", "Xcode") is appended to the system prompt so the result matches that app's register, trailing the preset's own instructions so the preset text stays a stable, cacheable prefix. Best-effort: silently dropped when unreadable or when FixLang itself is frontmost. Only Context-Aware Structured Text adapts markup to the app; every other preset uses the hint for tone alone.
- **Autocomplete** — ghost-text suggestions in the Ask AI input window only: once the prefix reaches **3 characters** and the **300 ms** debounce elapses, a greyed continuation appears at the caret. Both numbers are product decisions with a price: 3 (was 12) is inclusive and means the ghost fires for the short questions this window actually gets, but the threshold was doing most of the rate limiting, so the debounce (was 180 ms, inside a fluent typist's inter-keystroke gap) was raised to clear that gap and is now very nearly the only thing between a keystroke and a billed request — lower it and `DAILY_REQUEST_CAP` stops being a runaway backstop and becomes a budget an ordinary day can exhaust. **Tab** accepts it into the textarea; Tab over a selection is refused. **The first Esc clears the ghost and leaves the window open; a second Esc cancels the window.** Enter always submits the typed question, never an unaccepted ghost. Rendered through a plain mirror `<span>` — never `MarkdownView`, never `dangerouslySetInnerHTML` — because it is untrusted model output landing in an input surface. **The reply protocol is strict JSON, and that is a safety property rather than a formatting preference**: the model must answer `{"suggestion":"<continuation>"}`, `main/parseReply.ts` accepts nothing else, and **anything that does not parse as that exact shape yields NO suggestion** — refusal prose is not JSON, so it cannot reach the UI by construction rather than by a heuristic guessing at phrasings. This exists because a 9B local model, asked to continue `tes`, returned `Nothing to continue here as the input text "tes" appears to be an incomplete word or fragment without clear context for further` **as the suggestion** — it was CONTINUING the old prompt's closing sentence ("If a sensible continuation is not obvious, output nothing at all.") instead of obeying it, and that text painted as ghost text one Tab press from the user's question. Both observed refusal strings are pinned verbatim in `parseReply.test.ts` and `service.test.ts`. So: **no sentence in `AUTOCOMPLETE_SYSTEM_PROMPT` may be plausibly continuable as prose** — its first and last lines are literal JSON objects, the decline case is the value `{"suggestion":""}` rather than an instruction that can be obeyed in English, and the user prompt's trailing label is `JSON:`, not `Continuation:`. **The prompt states a PRIORITY rather than one continuation rule**: ends mid-word → finish that word; ends on a whole word, space or mark → add what comes next. Not cosmetic — typing `tes` used to produce the ghost ` is a common abbreviation for test.`, a valid continuation of the TEXT and useless as a completion of the WORD, because the old line (`Continue from exactly where the input stops, mid-word if it stops mid-word.`) described where the caret was without saying what to do at it. **A suggestion is always what gets APPENDED at the caret**, so `tes` completes to `t`, never `test` — carried by a literal example in the prompt (`"tes" -> {"suggestion":"t"}, not "test".`) rather than by another rule, because re-emitting the whole word is precisely what a model reaches for at the moment it is completing one; `prompt.test.ts` re-derives that example (typed + suggestion must equal the whole word), so an edit turning the demonstration INTO the forbidden output fails rather than reading fine. An ALREADY-COMPLETE word counts as done — `test` gets the phrase, not `ing`. Nothing in the buffer says whether it is finished or the start of `testing`, and the two errors are not symmetric: continuing past a boundary the user has crossed is a ghost they type through, while lengthening a word they had finished edits INSIDE it and a Tab aimed at the sentence silently rewrites it. **That branch is a request, not a guarantee** — 9 of 30 runs of `test` against `ornith-1.0-9b` still answered `ing`, and wordings that forbid letters (`add words, never letters`) bought that back by damaging the branch that matters, answering `test` for `tes`. **THE PROMPT ASKS; `sanitize.ts` ENFORCES.** Roughly **1 reply in 8** from `ornith-1.0-9b` returns the whole word regardless (`tes` → `{"suggestion":"test"}`, measured live against the real prompts), and nothing downstream compared the two — so the ghost painted `tes` + `test` = `testest` and Tab inserted exactly that: silent corruption of an input surface by untrusted model output. `sanitizeSuggestion` therefore takes the **prefix as a required second argument** (required, not defaulted, so no call site can read as sanitised while opting out) and strips a leading overlap between the suggestion and the tail of the prefix. **Four clauses, and every one of them is there to protect a legitimate repeat** — `had had`, `that that`, `New York, New York` are real text, and a guard that ate a genuine continuation would be worse than the bug: (1) **the caret must sit INSIDE a word** — a prefix ending on a space or a mark means the user FINISHED a word, so `he had ` + `had enough` is left exactly alone; only a mid-word caret can be glued into a non-word, which is the whole damage; (2) **the overlap runs from a WORD START to the caret**, so `he had` + ` had enough` cannot match (every candidate begins with a word character, that suggestion begins with a space) — the separator carries the meaning, and offsets INSIDE the trailing word are refused however tempting (`the do` + `og barks`), because a one-letter coincidence — `I like tea` + `a lot`, a model that simply forgot its leading space — would DELETE a word the model meant to add; (3) **longest match wins**, so `test tes` + `test tester` yields `ter`, never `t tester`; (4) the comparison **folds case** but only the SUGGESTION is ever cut, so `tes` + `Testing` gives `ting` and the user's own capitals survive. Bounded by `OVERLAP_LOOKBACK_CHARS` (80 — about thirteen words, and far inside `PREFIX_WINDOW_CHARS`, so it compares against exactly the text the model was shown); a re-emission starting beyond it strips nothing rather than guessing from a partial candidate. An overlap that empties the suggestion yields `null` — no ghost and no Tab affordance, not an empty one. **Missing an overlap costs a visibly wrong ghost the user declines; inventing one edits their text**, so every ambiguity resolves toward missing — which is also why scripts written without spaces get only the whole-run case. The live re-emission (`I want to tes` → `test this out.`, painting `I want to testest this out.`, with a perfectly sensible sentence behind the damage) is pinned verbatim in `sanitize.test.ts` beside the repeat table, the same way the refusal strings are. An empty-string suggestion means "nothing to suggest" and must paint no ghost and no Tab affordance, but it is NOT a protocol failure and must not warn. **Parse THEN sanitize, never the reverse**: a JSON string proves well-formed JSON only, and a unicode escape smuggles a control character past a raw-text inspection, so `sanitize.ts` still runs on the extracted field (it also strips complete markdown images — `![alt](url)` is never a continuation of a half-typed sentence — while leaving links alone, since those render as literal characters everywhere a suggestion can reach). **There is NO output-token ceiling — `maxOutputTokens` is not sent at all**, and `MAX_OUTPUT_TOKENS` (was 40) is gone. Explicit product decision: the model decides how long the reply is, and length is controlled by the system prompt, whose rule is now an imperative carrying a number (`Stop after one sentence; never emit more than 15 words.`) rather than the old category `At most one sentence.` — a category is judged by the model and one sentence can run eighty words. Say it plainly when touching this: **length is now a SOFT constraint a weak model can ignore**, and this feature has the receipts — the prompt that said `output nothing at all` was continued as prose by a 9B local model instead of obeyed. What actually protects the UI is the JSON envelope plus `parseReply.ts` (a ramble is not `{"suggestion":"…"}`, so it yields nothing) and, for a reply that *does* parse, `MAX_SUGGESTION_CHARS` (200) in `sanitize.ts`, which cuts it rather than refusing it. So nothing unbounded reaches the ghost span; what is unbounded is what the provider **bills** and how long the user **waits** — the debounce, `CACHE_TTL_MS`, the rate limit and `DAILY_REQUEST_CAP` all bound how MANY requests happen, and not one of them bounds how large a single reply is. Expressed as an ABSENT key, not `undefined` and not a sentinel: all five providers spread it conditionally (`options.maxOutputTokens !== undefined ? … : {}`), and Ollama maps it to `options.num_predict`, where a leaked value becomes a hard per-call token limit on a local model. `service.test.ts` asserts the key is absent from the request. **No `stop` sequence** any more: `["\n\n"]` cannot fire inside the envelope (a newline in the suggestion is an escape, not a line break) so it saves nothing on a rambling model, but it does fire on one that pretty-prints or preambles, and firing there removes the closing brace and turns a parseable reply into no suggestion. A suggestion belongs to one exact `{text, caret}` state; moving the caret invalidates it, enforced at the points that cost something (before the billed request, before it paints, and on accept) rather than on any one DOM event. Settings gets its own **Autocomplete tab** — placed beside Transform rather than inside General, since both are per-feature areas, and shown unconditionally because it is where the runtime toggle lives — carrying an enable toggle and a model picker (the `""` sentinel shows as "Same as Ask AI"), plus a privacy hint recommending a local provider (Ollama or LM Studio), since it sends text the user is still typing. Its per-day rollups — today, month-to-date, the 62-day series, and how much of the 1500/day request cap is spent — read from an **Autocomplete sub-tab of the dashboard's Usage tab**, last in that bar, not a top-level tab of its own: the dashboard's top level is one row per KIND of thing, and spend already has a row. Two consequences. `UsageSubTab` stays provider-shaped and the bar is composed by `buildUsageBar`, because autocomplete has no `ProviderId` and never will — it reports what THIS app spent, from local rollups rather than a billing API. And the "connect OpenAI or OpenRouter" card that used to REPLACE the whole tab when no usage-capable provider was connected is now a `providers` slot in that bar, still first, still what the user lands on: autocomplete needs no account (an Ollama-only user has zero provider sub-tabs and must still reach it), so a bar that simply omitted the empty case would have swallowed the only prompt telling that user what to connect. `requests` counts attempts DISPATCHED, not completions — an aborted request still bills. **The daily BUDGET is money, not requests**: `settingsAutocomplete.dailyCostCapUsd` (default **$5**, clamped to `[0, 100]`, editable in Settings → Autocomplete) is compared against the day's `estimatedCostUsd`, and `0` legitimately means "spend nothing" — hence `>=`, so a zero cap refuses before any spend exists, and hence a normalizer that falls back to the DEFAULT for anything unreadable rather than to `0`, which would look exactly like a broken feature. **A money cap cannot be the runaway stop, and that is why `DAILY_REQUEST_BACKSTOP` (10,000 dispatches) still exists beside it**: `estimatedCostUsd` sums PRICED responses only, so a local provider (a genuine `$0` — the ones the privacy hint recommends) never moves it by a cent, and a model `computeCost` refuses to price bills real money while recording `$0`. It is also TRAILING even where it works — spend is booked when a reply lands, so the request that crosses the line is already paid for and the cap refuses the NEXT one. The backstop is set past what typing can reach (the debounce caps a correct surface at ~3.33 dispatches/second, so 10,000 is ~50 minutes of uninterrupted typing) precisely so it reads as a runaway stop rather than a second budget — which is also why it is NOT on the wire and NOT drawn as a second bar. The two log at different reasons on purpose (`cap-reached` vs `request-backstop`): one says the user spent what they chose to, the other says a loop ran up a count no human produces, on spend the budget could not see. **The cap readout obeys the same money-honesty rule as everything else**: `resolveAutocompleteCapUsage` returns spend as an `AutocompleteMetric`, so a day whose responses all went unpriced renders its own "none of this could be priced" sentence instead of `$0.00 of $5.00` over a real bill, and draws no bar — Settings imports that same helper rather than dividing inline, because an inline `estimatedCostUsd / cap` there printed exactly that false zero and an existing test caught it. **A short-window rate limit in `main/service.ts` is the independent RATE stop beside it** — `RATE_LIMIT_PER_SESSION` 10 dispatches per surface per `RATE_LIMIT_WINDOW_MS` (1 s), `RATE_LIMIT_GLOBAL` 16 across all surfaces. It exists because everything between one keystroke and 1500 requests used to be enforced in the renderer: `sessionId` is derived from `event.sender.id` precisely BECAUSE the renderer is not trusted, yet the rate was left entirely to `GHOST_TEXT_DEBOUNCE_MS`, so a stuck effect, a wedged IME or a future surface with a bug could call `autocomplete-suggest` in a tight loop and main would dispatch every one until the cap tripped — minutes, all billed, and the 12 → 3 threshold change removed the headroom that used to hide it. **The arithmetic starts from a ceiling, not a guess**: the debounce is trailing and rearms on every change, so a correctly-working surface cannot exceed 1000/300 = 3.33 dispatches a second, i.e. at most 4 in any one-second window — reached not by a fast typist (whose keystrokes coalesce) but by a steady ~40 WPM one whose gaps sit just above the debounce. 10 is 2.5x a rate no correct renderer can reach, so no human can trip it; 16 is one surface spending its WHOLE allowance plus another typing flat out, so a runaway in one window cannot starve a second window's real user. A one-second window rather than a longer one at the same rate, because the window is also the burst size and the detection delay. **Placement is load-bearing: BELOW the cache, ABOVE `countDispatch`.** Below, because a cache hit calls no provider and returns text already paid for — charging the free path would refuse exactly the backspace-and-retype motion `CACHE_TTL_MS` exists to serve (and the cache key needs the resolved model ref anyway). Above, because `countDispatch` writes into the day the cap is read from, so refusing after it would book a request that never happened. It returns WITHOUT aborting the in-flight request, for the same reason the `countDispatch` refusal does. Session windows are LRU-bounded by `RATE_LIMIT_MEMORY_MAX_ENTRIES` (the `RESOLUTION_MEMORY_MAX_ENTRIES` precedent), so a caller churning `webContents` ids could evict its own bucket — which is exactly why the global window, keyed by nothing and never evicted, is there. **A consequence worth knowing before writing tests**: filling `CACHE_MAX_ENTRIES` at machine speed is now refused, so the cache-eviction test drives a fake clock at a step chosen to clear the limiter AND finish inside `CACHE_TTL_MS`, or it silently starts proving expiry instead of eviction. `estimatedCostUsd` sums PRICED responses only, and a day's `responses`/`tokenlessResponses`/`unpricedResponses` counters must agree with its sums or a month total shows money no day can account for. No SQLite history rows are written — only the aggregates — and there is no build-time feature tag; the feature ships **off** by default, and the runtime `enabled` toggle in Settings → Autocomplete is how a user opts in. **Every path that produces no ghost text now says so.** Main's seven refusals (`disabled`, `prefix-too-short`, `usage-unreadable`, `cap-reached`, `no-model`, `cache-hit`, `rate-limited`) each log a stable machine-readable `reason`; the two that silently kill the feature with nothing the user could guess (`no-model`, `usage-unreadable`) are `warn`, the routine ones `debug`, and `cap-reached` keeps its own once-per-day throttle. `rate-limited` is `warn` for a stronger reason than either: no typing can reach that limit, so a line there is our own bug or something pathological, and `debug` is the level most readers filter out — it carries `limitScope`/`limit`/`windowMs`/`dispatchesInWindow` and rides the same per-reason 60 s throttle, because a loop trips it thousands of times and unthrottled logging would become the second copy of the spam. The renderer's four non-dispatch paths (`composing`, `prefix-too-short`, `caret-moved`, `bridge-unavailable`) reach the Logs tab over the one-way `autocomplete-skip` channel — `send`, never `invoke`, because a round trip per keystroke is not worth a diagnostic — validated field by field in main and never spread. **The renderer half is the one that matters**: when it does not dispatch, main never runs, so without it "the window never asked" and "main refused" look identical (i.e. like nothing at all). Both ends throttle to **one line per reason per 60s** (`createSkipThrottle` in `shared/autocompleteDiagnostics.ts`), carrying a suppressed count; main's copy is the load-bearing one, since the renderer is untrusted and is the side under suspicion. **A dispatched suggestion that reaches nobody is logged too, and by whichever side can see it** — main's `superseded` (killed mid-flight by the next keystroke; it never answered, and only main has the model ref and the elapsed time) and the renderer's `reply-too-late` (it DID answer and the caret had moved on, which only the renderer can see). A third joins them, `unparseable-reply`: the reply arrived IN TIME and was not the JSON contract, so it was discarded. It is `warn` on the FIRST occurrence — unlike the two timing reasons, which start at `debug` because one late suggestion is ordinary fast typing — since there is no ordinary version of it: a model either answers in the contract or it does not, and one that does not fails on every request for as long as it stays selected, while the UI shows the same empty space it shows for a model with genuinely nothing to suggest. It rides the same 60 s per-reason throttle (a broken model produces it per keystroke) and carries `model`/`provider`/`replyLength`/`latencyMs` — **`replyLength`, never `replyTokens`, which the redactor would blank for containing `token`**; the reply itself never goes in the log, because it quotes the user's unsent text back (the real refusal above contains the typed fragment verbatim). None of the three subsumes another: steady typing against a slow model produces only the first, type-then-pause only the second, a model answering in prose only the third, and before them a 24-second model was indistinguishable from a broken feature. The renderer sends an id and NOTHING about the provider — a model name travelling up from it would be renderer-controlled text in an exportable file — and main answers it from its own per-session record of the last round trip (`takeAutocompleteResolution`, consumed by the read, bounded by `RESOLUTION_MEMORY_MAX_ENTRIES`); an unmatched id logs nothing rather than a line naming no model. Level is `debug` for a one-off and `warn` once the throttle's own suppressed count shows it recurring, because one late reply while typing fast is normal and every reply late is a misconfiguration nothing on screen reports. **No log line may carry the prefix, suffix or suggestion — lengths, ids and counts only**, and every context key is run through the real `redactLogContext` in a test, because a name merely *containing* `token`/`secret`/`clipboard`/`selected_text` persists as `"[REDACTED]"` with no error (the `selectionPoll` trap again).
- **Security guard rails** — four checks on the transform path, all configured from a **Security** dashboard tab (sixth of eight, between Logs and Autocomplete; the id lives in `dashboardTabIds.ts` like every other tab). (1) **Stale clipboard** — the selection is read by sending a copy keystroke and polling the pasteboard, so a copy that never landed silently transforms whatever was on the clipboard before; a 1 Hz tracker in `src/main/clipboard/` records when the pasteboard last changed and a read older than `clipboardMaxAgeSeconds` (**5**) is refused. (2) **Selection size** — over `maxSelectionChars` (**20 000**) asks first, because the cost of one accidental select-all is a bill and a whole document leaving the machine. (3) **Blocked apps** — a frontmost-bundle-id deny-list, defaulting to `com.1password.1password`, `com.agilebits.onepassword7` and `com.apple.keychainaccess`. (4) **Secret guard** — `off`/`confirm`/`mask`, default **`confirm`**, plus an opt-in high-entropy rule (default **off**, the one rule with a real false-positive rate). **`0` is the documented disable for the two numeric guards, and for the age guard it also stops the 1 Hz poll** — the interval is never scheduled when the guard is off, so switching it off costs nothing rather than merely ignoring a value it still computes. Junk in stored settings falls back to the DEFAULT, never to `0`: normalization that treats garbage as "disabled" turns a corrupt store into a silently unguarded app. `SecretGuardMode` is **one enum, not two booleans**, because `confirm && mask` is unreachable and encoding an impossible state means maintaining a resolver for it forever.
  - **`SECRET_SEND_SITE_POLICY` in `main/keybindings/secretGate.ts` is the ONE table** — `correction` masks and restores (the only path that pastes over a selection in another app), `promptGen` masks without restoring (its output is a generated prompt, so placeholders in it are the correct artifact), `ask` degrades `mask` to `confirm` (a free-form answer rarely echoes placeholders, so a restore would fail on most requests and permanently divert Ask to the popup). Autocomplete is deliberately absent: it fires per keystroke, where a modal is categorically impossible. Call sites READ the table; none re-derives it.
  - **`maskable` is why a masking mode still opens dialogs.** A rule reports `maskable: false` for a span it cannot prove covers the WHOLE credential; `maskSecrets` rolls that up as `fullyMaskable`, and the gate then applies `confirm` for that request with `reason: "partial-mask"` in the log. **The downgrade is TOTAL, not scoped to the offending span**: `fullyMaskable` is one boolean over the whole scan, the computed masking is dropped entirely, and on *Send anyway* every credential in that selection goes out verbatim — including ones that were individually maskable. Deliberate, because a half-masked send is exactly what this branch exists to prevent and `sentText` must be wholly masked or wholly the user's own text for the reply-side restore to have one shape. The dialog names every rule that matched but cannot show WHICH span was uncoverable, so the Settings copy (`security.secretGuard.limitations.body`) is what has to say it — and that copy is load-bearing, not decoration: it shipped once claiming masking meant "nothing is sent", which was false in both halves.
  - **Known detector limitation: two secrets concatenated with ZERO separator are seen as one match** (two AWS keys back to back, say). The rules are boundary-anchored and there is no word boundary mid-run. Inherent to boundary-anchored scanners, not a bug to fix — and worth knowing before trusting `matchCount`, which feeds the dialog string and the log line and nothing else.
  - **The log-redaction trap bites hardest here, and it is silent.** `redactLogContext` blanks any context key whose NAME merely *contains* `api_key|authorization|bearer|token|secret|password|clipboard|selected_text|original_text` — case-insensitively, no error, value replaced with `"[REDACTED]"`. Every natural name in this feature is a casualty: `clipboardAgeMs`, `clipboardChanged`, `clipboardMaxAgeMs`, `secretCount`, `secretsFound`, `maskedSecrets`, `tokensMasked`, `tokenRuleId`, `selectedTextLength`, `originalTextLength`. This already shipped once — `clipboardChanged` persisted as `"[REDACTED]"` and destroyed the metric, the same way `clipboardRead` did in the latency work. **The approved set is `presetId`, `guardReason`, `deniedBundleId`, `selectionAgeMs`, `ageLimitMs`, `textLength`, `charLimit`, `matchCount`, `ruleIds`, `guardMode`, `appliedMode`, `gateDecision`, `reason`, `placeholderCount`, `missingCount`, `confirmMs`, `pausedMs`, `delivery`, `pasteboardChanged`** — pinned in `secretGuard/shared/logKeys.test.ts`, which runs the REAL redactor rather than a copy of the regex. Two traps inside the trap: only KEYS are matched, so `{ reason: "stale-clipboard" }` survives while `{ "stale-clipboard": 1 }` does not; and rule ids are a VALUE, never a key — spreading `{[ruleId]: count}` blanks exactly nine of the ids and silently keeps `private-key-block` and `aws-access-key-id`, so the mistake looks like it worked in half the cases. Nothing that touches a real credential is loggable at all: `SecretMasking.replacements` holds real secrets as map values, and the key audit only defends key names.
  - **History stores the MASKED text on both sides when masking is on.** `original` is `sentText` and `corrected` is the model's raw reply, i.e. what actually crossed the wire, placeholders intact — never the restored text. The history DB is unencrypted under `userData` and the snapshot viewer has copy buttons, so storing the restore would durably recreate the exact exposure masking removed. Raw history after a *Send anyway* is correct: the dialog said the real value would be included. A restore that cannot replace every placeholder forces delivery to the **popup** regardless of the preset and the global setting (`resolveSecretGuardOutputMode`), because pasting a partial restore writes a mixture of real secrets and placeholders over the user's selection with nothing to tell them apart.
  - The confirm dialog's wait is bracketed by `aroundDialog`, which wraps ONLY the modal await — never the whole gate — so the overlay spinner is not blinked on every transform in `confirm` mode, where the vast majority detect nothing and open no dialog. The same wrapper brackets the downgraded dialog. Latency pauses across it (`pausedMs`), so a user reading a dialog does not land in a phase delta. `aroundDialog` is genuinely generic, and `Mock<…>` flattens a generic signature, so a bare `vi.fn()` will not satisfy it in a test — pass a real generic wrapper.
- **Prompt generation** — PromptGen window builds AI prompts from selected text (`Control+Shift+G`). Feature-tagged, so released builds ship it OFF.
- **Profiles** — named configurations, cycled with `Control+Shift+P`; a switch reloads hotkeys, settings, and history together.
- **Multi-provider** — OpenAI, OpenRouter, AWS Bedrock, Ollama and LM Studio can all be connected at once. Every connected provider's models appear in one grouped picker, and any preset can use any of them regardless of the profile default. Bedrock takes an access key ID + secret access key + AWS region; the two local providers take a host/port.
- **Admin keys** — an OpenAI Admin API key or an OpenRouter provisioning key unlocks that provider's Usage sub-tab. Keys live main-process-only, encrypted at rest, scoped to one profile + provider + slot, and a key that provably belongs to another slot is refused at paste time instead of 401ing later.
- **History** — SQLite transform + Ask + PromptGen history with cost tracking. A row's eye control opens the raw completion snapshot (prompts, responses, usage) with a chat view that also states prompt/completion tokens and the reasoning effort used.
- **Analytics** — Overview (token stats with an N/A-aware estimated-cost hint, preset donut + time series, token activity calendar) and Models (token-usage bars, Model Breakdown donut + ranked table) share one All/30d/7d range.
- **Usage** — account-level spend and token usage, one sub-tab per connected provider that has a billing API (OpenAI, OpenRouter). OpenAI reports tokens per model, spend per line item and spend per project — never a per-model dollar figure or a credit balance, because its API exposes neither.
- **Tray popover** — Providers card (one tab per usage-capable connected provider: OpenRouter credit, OpenAI recent billed spend), language switch, output-mode switch, global model + reasoning-effort selectors, update check, dashboard opener.
- **Logs** — structured, redacted JSONL under `userData/logs/{YYYY-MM-DD}/fixlang.jsonl`; Logs tab with multi-select level filter, search, copy/export, virtual infinite scroll, timezone stated once in the footer.
- **Latency logging** — one `correction.latency` info line per hotkey press states what the user actually felt: `totalMs` from press to result in front of them (paste keystroke returned, or popup shown) plus a `phases` breakdown (`keystrokeSent`, `selectionPoll`, `aiRequest`, `delivery`) and an `outcome`. Every press that reaches the handler logs one line and never two: abort (`no-selection`) and failure (`failed`) paths finish the timer too, and the first `finish` wins so a throw *after* delivery cannot relabel a real `delivered` measurement. (A press swallowed by `withHotkeyThrottle` logs nothing — it never starts a timer.) **Phase names are a closed set (`LATENCY_PHASE_NAMES`) for a reason**: `redactLogContext` blanks any context key merely *containing* `clipboard`/`token`/`secret`/`selected_text`, so the obvious name `clipboardRead` persisted as `"[REDACTED]"` and destroyed the metric with no error — hence `selectionPoll`, and a test that runs every phase name through the real redactor. Post-delivery bookkeeping (cost, history write, IPC) sits outside the measurement — the user never waits for it. Ask AI is split in two, because the gap between its hotkey and its submit is the user typing: the hotkey press measures press → input window (`input-shown`), and `askFlow.ts` starts a fresh timer at submit (`Ask latency`).
- **Hotkeys** — every transform preset hotkey plus PromptGen and profile-switch bindings are remappable; conflicts are refused before save, and a default-sourced binding yields to one the user already claimed.
- **About** — two sub-tabs: **App updates** (version check + one-click Homebrew upgrade) and **User guide**, onboarding copy built from the user's REAL config (their presets, hotkeys, output mode, connected providers) with jump links into Settings and the dashboard tabs.
- **Appearance & language** — 149 terminal-inspired themes; English and Japanese, switchable without restart.

## Purpose

User data stays local — API keys, history, and logs never leave the machine except to the providers a profile has connected, and each provider only ever sees its own key. Profile and hotkey state must stay consistent across switches; silent breakage there is worse than a loud failure.

- **The packaged app ships no `node_modules`** (`build.files` excludes it) — every runtime dependency must be inlined by Vite into `out/`. Adding a dependency and importing it passes `dev`, `test`, and `lint` unchanged; only `bun run check:bundle` against a real `bun run build` catches a dependency Vite left external. The scanner lives in `src/features/core/shared/bundleExternals.ts` (AST walk via the TypeScript compiler API, not a regex); `scripts/check-bundle-externals.ts` is a CLI-only wrapper that runs under **bun**, whose TS parser differs from vitest's esbuild — which is why an integration test drives that exact file under bun. `ALLOWLIST` is empty on purpose: an entry hides a `MODULE_NOT_FOUND` for users instead of fixing it. Every packaging script (`pack`, `pack:mac`, `pack:mac:prod`, `release:mac`) runs the check. See [Bundle externals](.claude/skills/fixlang/fixlang-bundle-externals/SKILL.md).
- **`dependencies` vs `devDependencies` no longer signals what ships** — nothing resolves from `node_modules` at runtime, so the split is bookkeeping only; what ships is whatever Vite inlined into `out/`. Do not "fix" a runtime import by moving its package between the two sections.
- **Feature tags are opt-in** — features listed in `src/features/core/shared/features.ts` are excluded unless the build carries their tag (`FIXLANG_FEATURES=promptgen` env, or `--promptgen` CLI). Flag-off builds emit no renderer bundle for the feature and skip its hotkey, IPC handlers, and settings tab. Read flags at runtime via `isPromptGenEnabled()`, never `__FEATURE_PROMPT_GEN__` directly (the define is absent under vitest). Plain `bun run build` (what the release workflow runs) ships PromptGen OFF.

## Internationalization (i18n)

The app supports **English** and **Japanese** (easily extensible to a third language). All user-facing text in the renderer and main process is translatable via `t()` (renderer) or `mainT()` (main process).

### Catalog structure

Translation strings live in `src/features/i18n/shared/locales/{en,ja}/` as per-namespace JSON files (`common.json`, `dashboard.json`, `tray.json`, `notifications.json`, etc.). This split prevents merge conflicts when separate features add keys to the same catalog.

- Keys are globally unique and dotted (`"settings.general.language.label"`).
- English (`en/`) is the source of truth — every key must exist there; Japanese (`ja/`) may be partial (missing keys fall back to English).
- Both catalogs are merged at build time into `EN_CATALOG` and `JA_CATALOG` in `src/features/i18n/shared/locales/index.ts`.
- Key names are type-checked at compile time: `t("key")` is a compile error if `"key"` is absent.

### Add a translatable string (recipe)

1. **English**: Add the key-value pair to `src/features/i18n/shared/locales/en/{namespace}.json`:

   ```json
   { "overview.stat.sessions": "Sessions" }
   ```

2. **Japanese**: Add the translation to `src/features/i18n/shared/locales/ja/{namespace}.json`:

   ```json
   { "overview.stat.sessions": "セッション" }
   ```

3. **Use it**: The key is type-checked at compile time — a typo will be caught by the TypeScript compiler and displayed in your editor:

   ```tsx
   import { useI18n } from "~/renderer/i18n/useI18n";
   const { t } = useI18n();
   <h1>{t("overview.stat.sessions")}</h1>
   ```

### Plurals

English defines both singular and plural variants; Japanese defines only the plural (other) variant. Use the base key plus a numeric `count` param:

```json
// en/history.json
{ "history.count_one": "{count} transform", "history.count_other": "{count} transforms" }

// ja/history.json
{ "history.count_other": "{count} 件の変換" }
```

```tsx
const { t, formatNumber } = useI18n();
// Calls t("history.count_one") if count is 1, t("history.count_other") otherwise;
// the raw count is never shown, so never pass count as a string.
t("history.count", { count: 12 })  // "12 transforms" (EN) / "12 件の変換" (JA)
```

### Number and date formatting

`t()` locale-formats every numeric param automatically (grouping separators, native digits). Pre-formatted values (currency, dates, fixed decimals) are passed as strings so they are not re-formatted:

```tsx
const { t, formatCurrency, formatDate } = useI18n();
t("overview.tokenBudget", {
  tokens: 123456,           // auto-formatted: "123,456" (EN) / "123,456" (JA)
  pct: 50,
  budget: 100_000,
});

// For dates and currency, format first, pass as string:
t("model.lastUsed", {
  date: formatDate(new Date()),      // "Jul 25, 2026" (EN) / "2026年7月25日" (JA)
  cost: formatCurrency(12.5, "USD"), // "$12.50"
});
```

### Adding a third language

Add the language to `LOCALE_CODES` and `LOCALE_META` in `src/features/i18n/shared/registry.ts`; then create one JSON file per namespace under `src/features/i18n/shared/locales/{code}/` (e.g., `src/features/i18n/shared/locales/fr/common.json`). The language picker grows automatically; IPC, formatters, and storage need no changes.

### Main process strings

Notifications and window titles are built in the main process, which has no React context. Use `mainT()` instead of `useI18n()`:

```ts
import { mainT } from "~/main/i18n";

new Notification({
  title: mainT("notification.title"),
  body: mainT("notification.body", { name: "John" }),
}).show();
```

### Locale persistence and broadcast

- The user's locale choice is persisted via `electron-store` in `src/features/i18n/store/localeStore.ts`.
- On first run, the system locale (from `app.getLocale()`) is auto-detected and stored.
- Changing the language via Settings broadcasts the new locale to every open window (tray, dashboard, PromptGen) via IPC, so they update immediately without an app restart.
- See `src/features/i18n/main/locale.ts` for the IPC handlers; `src/features/i18n/preload/locale.ts` for the bridge; `src/renderer/i18n/I18nProvider.tsx` for the context subscription.

## CI

- **PR + push to `main`** — `.github/workflows/ci.yml` runs two independent jobs on `ubuntu-latest` (Bun 1.3.14; the test job also sets up Node 24 for `node:sqlite`): a `lint` job, and a `test` job fanned out over a 3-way `--shard` matrix with `fail-fast: false` so one shard's failure still reports the others. Concurrency cancels superseded runs. Release packaging stays in `release.yml` only.
- **Vitest runs as two projects, and the split is the whole reason CI is fast** — `node` (everything outside `src/renderer/`) and `renderer` (`src/renderer/**`, `jsdom`). jsdom costs roughly 0.75 s of environment setup **per test file**, so running all 188 files under it spent ~143 s of cumulative environment time for the 33 files that actually need a DOM; the split cut a full local run from 24.7 s to 13.4 s with no change to what is tested. A new test outside `src/renderer/` that reaches for `document`/`window` will fail under the `node` project — move it under `src/renderer/`, or give that one file a `// @vitest-environment jsdom` docblock, rather than widening the `renderer` project's globs.
- **Coverage is off by default** (`coverage.enabled: false`); run `bun run test:coverage` for a report. Nothing gates on it, and a sharded run only ever sees its own third of the files, so a coverage number collected in CI would be a lie.

## Release & Distribution

- **Trigger** — bump `package.json` to a strictly higher stable semver, PR to `main`, merge. Push to `main` fires `.github/workflows/release.yml` (`prepare` on ubuntu creates the `v<version>` tag; `release` on macos-14 runs lint → test → `i18n:check` → build → `check:bundle` → DMG, validates the DMG, publishes `FixLang-<v>-arm64.dmg` + `SHA256SUMS.txt`). The DMG is compressed with ULFO (LZFSE) via `build.dmg.format` and ships only the `en`/`ja` Electron locale paks (`build.mac.electronLanguages`); with `node_modules` gone from `app.asar` that lands at ~102 MiB. Between *Build renderer and processes* and *Build unsigned arm64 DMG*, a `bun run check:bundle` step AST-scans the built CommonJS for bare `require()` specifiers so a future dynamic dependency cannot silently become a `MODULE_NOT_FOUND` in a shipped app. Docs-only pushes no-op (version already public).
- **The DMG validation step is the packaged-artifact half of that guard** — it mounts the image, matches `CFBundleShortVersionString` against `package.json`, then asserts via `bunx @electron/asar list` that `app.asar` holds **no** `/node_modules/` entries and **does** hold `/out/renderer/` (a missing renderer ships a white-screen app). `@electron/asar` is a declared devDependency on purpose: the bare `asar` bin was only hoisted transitively through electron-builder, and `bunx asar` would otherwise fetch the deprecated standalone package from the registry.
- **Homebrew** — public tap `anhdd-kuro/homebrew-tap` auto-syncs verified releases into `Casks/fixlang.rb`; users run `brew install --cask anhdd-kuro/tap/fixlang` and `brew update && brew upgrade --cask fixlang`. arm64-only, unsigned — never automate Gatekeeper/`xattr`.
- **In-app update** — `updates:install` starts a detached `/bin/sh` helper that waits for FixLang to exit, runs `brew update && brew upgrade --cask fixlang` (`NONINTERACTIVE=1`), then reopens the app; the app quits itself right after. brew is resolved only from `/opt/homebrew/bin/brew` or `/usr/local/bin/brew` (never PATH), and the button is off unless `<prefix>/Caskroom/fixlang` exists. A `pending-update.json` marker under `userData` reports a stalled upgrade on the next launch; helper output goes to `userData/logs/homebrew-update.log`.
- **The check asks Homebrew, not GitHub** — for a cask install `checkForUpdates` offers `HomebrewUpgrader.getInstallableVersion()`, because Homebrew is what the button runs. GitHub is queried in parallel but only supplies release notes and the DMG size, and only when it describes the exact version being offered. A published release the tap has not synced yet is reported as `up-to-date` + `tapPendingMessage`, never as an offer — but it still carries that release's notes and points `getReleaseUrl()` at its tag, so the panel shows what changed next to a **Download from GitHub** button. Only the DMG size is withheld, because the download bar it feeds belongs to an install that cannot start. Cost control: the routine check reads the local tap clone (`getInstallableVersion(false)`, no `brew update` — that is a git fetch across every tap) and pays for one refresh only when GitHub shows something newer. Manual DMG installs, and casks whose brew probe returns null, still fall back to GitHub.
- **Two version sources** — **GitHub Releases** is what publishes a version (and, for manual DMG installs, what the check reads), the install runs **the Homebrew tap**, and the tap lags the release (cron, up to 6h). `installUpdate` therefore probes `brew info --cask fixlang --json=v2` (after `brew update`) and refuses to quit when the tap is still behind. Never delete that gate: `brew upgrade` exits **0** on "already installed", so without it the app quits and reopens unchanged and the button looks dead. A null/unparseable probe means "unknown" → proceed; only a *parsed lower* version blocks.
- **An unchanged version on relaunch is not proof of failure** — the app quits in under a second, Homebrew keeps downloading ~101.6 MiB for a minute or more, and a user who reopens FixLang meanwhile lands in `reconcileLastInstall` with the old bundle still in place. Treating that as failure clears the marker, shows "Homebrew did not finish the last update", and re-arms the button, so the next click starts a second `brew upgrade` that dies on the first one's **download lock**. The marker therefore carries `startedAt`, and reconcile returns `in-progress` (keep marker, keep the button inert, poll the Caskroom) until either `<prefix>/Caskroom/fixlang/<target>` appears → `restart-required`, or `UPGRADE_GRACE_MS` (20 min) passes → `failed`.
- **Download happens while the app is alive** — `installUpdate` runs `brew fetch --cask fixlang` first (fills the download cache only, installed bundle untouched) and publishes a `downloading` phase with byte progress read by `statSync` from `<HOMEBREW_CACHE>/downloads/*--FixLang-<v>-arm64.dmg[.incomplete]`. Progress is read from the growing cache file, never parsed out of brew's output, and the denominator is the GitHub release asset `size`. Only after the fetch succeeds does the app quit; the detached helper then just runs `brew upgrade` off the cache (no `brew update` — the tap probe already refreshed it), so the app is away for seconds instead of a minute.
- **`open -b` cannot replace a running app** — the helper's closing `open -b com.fixlang.app` resolves with `preferIdentical`, so when FixLang is already running it merely *focuses* the stale process while `/Applications` already holds the new bundle. That is why the `restart-required` phase exists, and why its restart re-executes `process.execPath` (`app.relaunch()` + `app.exit(0)`) instead of shelling out to `open`.
- **The bundle id is not a unique app** — a `pack:mac` build sitting in a checkout used to carry `com.fixlang.app` too, so the helper's closing `open -b` could reopen *that* copy right after a successful upgrade, and the user landed on an older version. Two defences: the helper reopens the recorded `.app` path (`open -a "<path>"`, id only as fallback), and `pack:mac` now builds as `com.fixlang.app.dev` / `FixLang Dev` (use `pack:mac:prod` for a production-identity local build; `pack:install` already does). Dev builds still share `userData` — the packaged `package.json` keeps `name: fix-lang`, which is what `app.getName()` reads.
- **A changed version is not proof of success** — `reconcilePendingInstall` compares against `toVersion` and against the recorded `appPath`, not merely "differs from `fromVersion`"; otherwise reopening a stray *older* copy reports as a completed update. A mismatched path yields `wrong-bundle` → `restart-required` carrying `wrongBundleMessage`, and that restart opens `pending.appPath` instead of re-executing `process.execPath` (which would just relaunch the wrong copy forever).
- **Traps** — release Test step needs Node 24 on macos runners (`node:sqlite` builtin); tap cask generation + `brew style/audit` have several traps. See the gotcha below before touching release or tap code.

## Known Gotchas

- [Profile state](.claude/skills/fixlang/fixlang-profile-state/SKILL.md) — profile switch must atomically reload hotkeys + settings UI + history; connecting a provider does NOT wipe presets.
