# Security guard rails — gotchas

Four checks on the transform path, configured from **Settings → Security**; the
**Security** dashboard tab is the read-only roll-up of what they did.
The feature summary lives in [AGENTS.md](../../../../AGENTS.md); everything below is
the part that bites.

## The guards themselves

**Security guard rails** — four checks on the transform path, all configured from the **Security** settings tab (`SettingSecurity.tsx`, after Autocomplete and before Appearance in `visibleSettingsTabIds()`). The **Security** DASHBOARD tab (sixth of seven, between Logs and About; the id lives in `dashboardTabIds.ts` like every other tab) is a different thing: read-only guard activity, range-aware like Overview and Models. (1) **Stale clipboard** — the selection is read by sending a copy keystroke and polling the pasteboard, so a copy that never landed silently transforms whatever was on the clipboard before; a 1 Hz tracker in `src/main/clipboard/` records when the pasteboard last changed and a read older than `clipboardMaxAgeSeconds` (**5**) is CONFIRMED before it is sent. **Confirm, not block, and the age carries an ORIGIN**. `clipboardAge()` returns `{ms, origin}`: `"change"` means a copy was observed happening and the number is a real age; `"baseline"` means the text was already on the pasteboard the first time FixLang looked, so the elapsed time since that sighting is a LOWER BOUND, not an age. A bare number reported the pre-launch password as `0 ms` and waved it through for one whole limit window after every start — which is when a menu-bar app is likeliest to be holding something from before it was running — so a `baseline` origin always confirms, whatever the number says. It is a CONFIRM because the observer folds an identical re-copy into "no change" (same hash) and Electron exposes no pasteboard change counter: under a hard block, a user who deliberately re-copied the same text could not clear it by doing the one thing that ought to clear it, and had to copy something else first. The deny-list stays the only unoverridable verdict — it is a rule about WHERE text may come from, with nothing left to weigh. Only ONE confirm is raised per selection (age beats size), because a user clicking through two dialogs for one press learns to click through them everywhere. (2) **Selection size** — over `maxSelectionChars` (**20 000**) asks first, because the cost of one accidental select-all is a bill and a whole document leaving the machine. (3) **Blocked apps** — a frontmost-bundle-id deny-list, defaulting to `com.1password.1password`, `com.agilebits.onepassword7` and `com.apple.keychainaccess`. (4) **Secret guard** — `off`/`confirm`/`mask`, default **`confirm`**, plus an opt-in high-entropy rule (default **off**, the one rule with a real false-positive rate). **`0` is the documented disable for the two numeric guards, and for the age guard it also stops the 1 Hz poll** — the interval is never scheduled when the guard is off, so switching it off costs nothing rather than merely ignoring a value it still computes. Junk in stored settings falls back to the DEFAULT, never to `0`: normalization that treats garbage as "disabled" turns a corrupt store into a silently unguarded app. `SecretGuardMode` is **one enum, not two booleans**, because `confirm && mask` is unreachable and encoding an impossible state means maintaining a resolver for it forever.

## The activity roll-up

**The dashboard tab counts log lines, and that is a deliberate trade.** `get-security-stats` walks the persisted JSONL day folders (`features/guards/main/securityStats.ts`), keeps the guard lines, and folds them in the pure `features/guards/shared/securityStats.ts`. There is no counter store beside the logs, because a second set of numbers could disagree with the lines it was counting and the disagreement would be invisible. The cost, stated in the panel: **`logs:clear` resets the numbers.**

- **Events are identified by the `guardEvent` / `gateDecision` CONTEXT KEYS, never by the message text.** Rewording a log message must not zero a metric. `guardEvent` (`blocked` / `declined` / `context-dropped`) exists specifically because `guardReason` alone cannot tell a real block apart from an Ask context-drop — both carry the same reason values. Any new guard log line needs it, and the key is on the approved list in `logKeys.test.ts` (`guardEvent` survives `redactLogContext`; `guardMode` and `gateDecision` already did).
- **A selection-guard line with `guardReason` but NO `guardEvent` is a pre-roll-up line, and it is counted as `legacyEvents` — named, never classified.** `guardEvent` was added by the same change that added the roll-up, so every guard line in an upgraded user's archive lacks it; dropping them made the panel claim "no guard has fired" while the Logs tab showed otherwise. They cannot be classified: a legacy block and a legacy Ask context-drop wrote the *same* context keys (`guardReason` + `deniedBundleId`), which is precisely why `guardEvent` exists. So they land in one disclosed bucket that feeds `eventCount` and `lastEventAt` and renders as its own notice above the cards.
- **An unrecognised decline reason is DROPPED, not folded into a neighbour.** Add a fifth confirm reason to `selectionGuards.ts` and the dashboard shows a missing metric until `countSelectionGuardEvent` learns about it — which is the failure you can see, versus inflated stale-clipboard declines, which is the one you cannot.
- **There is no denominator and there never will be from this source.** A guard that ALLOWS logs nothing, so every number is a count of times a guard acted. Do not divide by a transform count from history: that is a different population (per-preset rows, no combos, no Ask context reads) and the ratio would look authoritative while being wrong.
- **Only the secret gate logs both arms of its dialog** (`confirmed` and `declined`); the selection confirms log only the decline. An accepted size/age confirm continues into the normal request path, so "how often did I say yes" is answerable for secrets and not for the others.
- **A malformed range or reply REJECTS on both sides of the bridge** rather than returning `EMPTY_SECURITY_STATS`. All-zeros reads as "no guard ever fired", which is a different claim from "the numbers could not be read"; the panel's error state is the honest one.
- **Day folders are LOCAL days, entry timestamps are UTC**, so the range prune keeps one surplus older folder and the exact window comes from the per-entry filter. Dropping the surplus folder loses real events at the boundary; skipping the entry filter silently widens the window by a day. Both halves are pinned in `securityStats.test.ts`.
- **The walk breaks at the first out-of-range folder** because `listPersistedDays()` is newest-first. Without the break, every range switch pays for the whole archive.

## Traps

- **`SECRET_SEND_SITE_POLICY` in `main/keybindings/secretGate.ts` is the ONE table** — `correction` masks and restores (the only path that pastes over a selection in another app), `promptGen` masks without restoring (its output is a generated prompt, so placeholders in it are the correct artifact), `ask` degrades `mask` to `confirm` (a free-form answer rarely echoes placeholders, so a restore would fail on most requests and permanently divert Ask to the popup). Autocomplete is absent from the table because it fires per keystroke, where a modal is categorically impossible — **but it is no longer ungated**. As of 0.23.0 ghost-text requests carry the ATTACHED Ask context, so the user's SELECTION reached a provider once per debounce interval, ahead of the submit-time `ask` gate; the exclusion had been justified partly on autocomplete sending only text typed into FixLang's own window, and that half stopped being true. So `service.ts` scans prefix + suffix + attached context whenever `mode !== "off"` and REFUSES to dispatch (`secret-in-text`, the eighth skip reason) instead of asking — the only guard shape that fits a surface with no place to put a question. **The scan sits ABOVE the cache**, unlike every other refusal there: the others are about cost, and a cache hit costs nothing, while this one is about what leaves the machine and must hold for as long as the credential is on screen rather than until the first reply is cached. `secretGuardStore` is imported LAZILY (the `makeAIRequest` precedent) — a module-scope import drags a real `electron-store` into the module graph of everything importing this file and breaks three unrelated test suites with `Please specify the projectName option`. `warn`, not `debug`, because the user is typing something credential-shaped and the ghost silently stops appearing; the line carries `ruleIds` as an array VALUE and no length at all, since on a prefix that is mostly one credential a length is most of a fingerprint. **What it cannot do**: protect a credential still being typed — a half-typed key matches no boundary-anchored rule, and earlier dispatches already carried what was typed so far. The Security tab copy says exactly that in both locales. Call sites READ the table; none re-derives it.

- **`maskable` is why a masking mode still opens dialogs.** A rule reports `maskable: false` for a span it cannot prove covers the WHOLE credential; `maskSecrets` rolls that up as `fullyMaskable`, and the gate then applies `confirm` for that request with `reason: "partial-mask"` in the log. **The downgrade is TOTAL, not scoped to the offending span**: `fullyMaskable` is one boolean over the whole scan, the computed masking is dropped entirely, and on *Send anyway* every credential in that selection goes out verbatim — including ones that were individually maskable. Deliberate, because a half-masked send is exactly what this branch exists to prevent and `sentText` must be wholly masked or wholly the user's own text for the reply-side restore to have one shape. The dialog names every rule that matched but cannot show WHICH span was uncoverable, so the Settings copy (`security.secretGuard.limitations.body`) is what has to say it — and that copy is load-bearing, not decoration: it shipped once claiming masking meant "nothing is sent", which was false in both halves.

- **Known detector limitation: two secrets concatenated with ZERO separator are seen as one match** (two AWS keys back to back, say). The rules are boundary-anchored and there is no word boundary mid-run. Inherent to boundary-anchored scanners, not a bug to fix — and worth knowing before trusting `matchCount`, which feeds the dialog string and the log line and nothing else.

- **The log-redaction trap bites hardest here, and it is silent.** `redactLogContext` blanks any context key whose NAME merely *contains* `api_key|authorization|bearer|token|secret|password|clipboard|selected_text|original_text` — case-insensitively, no error, value replaced with `"[REDACTED]"`. Every natural name in this feature is a casualty: `clipboardAgeMs`, `clipboardChanged`, `clipboardMaxAgeMs`, `secretCount`, `secretsFound`, `maskedSecrets`, `tokensMasked`, `tokenRuleId`, `selectedTextLength`, `originalTextLength`. This already shipped once — `clipboardChanged` persisted as `"[REDACTED]"` and destroyed the metric, the same way `clipboardRead` did in the latency work. **The approved set is `presetId`, `guardReason`, `deniedBundleId`, `selectionAgeMs`, `ageLimitMs`, `textLength`, `charLimit`, `matchCount`, `ruleIds`, `guardMode`, `appliedMode`, `gateDecision`, `reason`, `placeholderCount`, `missingCount`, `confirmMs`, `pausedMs`, `delivery`, `pasteboardChanged`** — pinned in `secretGuard/shared/logKeys.test.ts`, which runs the REAL redactor rather than a copy of the regex. Two traps inside the trap: only KEYS are matched, so `{ reason: "stale-clipboard" }` survives while `{ "stale-clipboard": 1 }` does not; and rule ids are a VALUE, never a key — spreading `{[ruleId]: count}` blanks exactly nine of the ids and silently keeps `private-key-block` and `aws-access-key-id`, so the mistake looks like it worked in half the cases. Nothing that touches a real credential is loggable at all: `SecretMasking.replacements` holds real secrets as map values, and the key audit only defends key names.

- **Restoration is where a provider that never saw the credential still gets to place it.** `restoreSecrets` checks four things in order, and the middle two exist because "replace every occurrence" is not a safe definition of restore: (1) every placeholder present, (2) **MULTIPLICITY preserved exactly** — one occurrence in, two out, is the model materializing the secret somewhere the user's own text never had one, (3) **no RELOCATION into a link token** unless the sent text already had that placeholder inside one, which is the attack the count check alone misses (multiplicity intact, reply reads as an ordinary rewrite, restored credential lands in `https://attacker.example/?k=…` for the receiving app to unfurl) — compared against where it WAS, not banned outright, or `url-credentials` could never round-trip a DSN at all, (4) no salted residue. Position beyond that is NOT constrained: a rewrite is allowed to move text around, that being the point of the request. Every failure funnels to `resolveSecretGuardOutputMode`, which forces the popup — refusing costs a paste, accepting costs the credential.

- **History stores the MASKED text on both sides when masking is on.** `original` is `sentText` and `corrected` is the model's raw reply, i.e. what actually crossed the wire, placeholders intact — never the restored text. The history DB is unencrypted under `userData` and the snapshot viewer has copy buttons, so storing the restore would durably recreate the exact exposure masking removed. Raw history after a *Send anyway* is correct: the dialog said the real value would be included. A restore that cannot replace every placeholder forces delivery to the **popup** regardless of the preset and the global setting (`resolveSecretGuardOutputMode`), because pasting a partial restore writes a mixture of real secrets and placeholders over the user's selection with nothing to tell them apart.

- **A warning that is the only explanation for something the app just did differently goes through `showNotificationWithFallback`, never a bare `new Notification(...).show()`.** FixLang ships unsigned, and macOS refuses notifications from an unsigned bundle with `Application is not code signed` — reported on the async `failed` event, NOT as a throw, so the naive call reports success and shows nothing. The restore-failure warning shipped that way once, which left the user with a popup full of placeholders and no reliable statement of why.

- The confirm dialog's wait is bracketed by `aroundDialog`, which wraps ONLY the modal await — never the whole gate — so the overlay spinner is not blinked on every transform in `confirm` mode, where the vast majority detect nothing and open no dialog. The same wrapper brackets the downgraded dialog. Latency pauses across it (`pausedMs`), so a user reading a dialog does not land in a phase delta. `aroundDialog` is genuinely generic, and `Mock<…>` flattens a generic signature, so a bare `vi.fn()` will not satisfy it in a test — pass a real generic wrapper.
